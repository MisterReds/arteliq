# Организация работы: кто, на какой модели, в каком порядке

Цель: проекты, которые идут часами и не упираются в лимит сильной модели, при результате, проверенном независимо.
Документ задаёт целевую схему (версия 2, 2026-11-10) и отмечает, что из неё уже работает. Реализация — этапы M1 и M3
[PLAN-1.0.md](PLAN-1.0.md); порядок и статус — `roadmap.yaml`.

Основания: прогон S-cloud-1 (27,5% токенов на сильной модели, $2,31 за шесть задач), статья DeepSeek о
супер-агенте (абляция: команда тратит в 2–4 раза больше токенов чтения кэша, чем одна сессия, и выигрывает в
стабильности времени), руководство Anthropic по выбору модели от 2026-11-09 (усилие раньше модели; дёшево сначала с
проверкой; команда только там, где есть ширина; «советник» сильной модели не окупается).

## 1. Семь правил

1. **Независимость важнее цены.** Работу принимает другой провайдер на среднем профиле, а не более дорогая модель
   того же провайдера. Сильная модель не делает проверку надёжнее; другой взгляд — делает.
2. **Модель выбирает код, а не модель.** Профиль запуска — чистая функция от роли, сложности цели, номера попытки и
   причины прошлого провала. Решение и причина пишутся в журнал решений.
3. **Профиль — это модель и усилие.** Сначала поднимается усилие, потом модель. Следующая модель начинает с усилия
   ниже.
4. **Дёшево сначала, проверка решает.** Первая попытка — средний профиль, среднее усилие. Различающие проверки и
   ревью отсекают неудачи; дороже повторяется только провалившееся.
5. **Команда — только там, где есть ширина.** Одна зависимая цепочка или объём, который помещается в один
   контекст, выполняется одним исполнителем. Воркеры добавляются по факту, а не по привычке.
6. **Контекст — это расход.** Свежий контекст на задачу; сильный профиль видит только сводки постоянного размера;
   модель внутри сессии не меняется (кэш принадлежит модели — смена означает новую сессию со сводкой).
7. **Малые модели — только для одношаговых ролей.** Классификация, сводка, бриф, навыки. Длинных агентных циклов
   на дешёвом профиле нет.

## 2. Профили

Имена моделей живут только в конфиге (`tiers.models`); ниже — соответствие по умолчанию для подписки Claude.

| Профиль | Модель по умолчанию | Усилие | Роли | Запрещено |
|---|---|---|---|---|
| `cheap` | Haiku | низкое | intake, чат-консьерж, библиотекарь, рефайнер, диагност, сборщик сводок | циклы с инструментами длиннее нескольких шагов |
| `medium` | Sonnet | среднее → высокое | воркер, ревьюер, тестер, планировщик обычной цели | принимать свою же работу |
| `strong` | Opus | среднее | планировщик сложной цели; решение по застрявшей задаче | писать код, читать файлы и логи целиком, финальная приёмка |
| `frontier` | самая сильная модель каталога | среднее | только по правилу владельца: архитектура очень крупной цели, большая миграция | включаться автоматически |

Что меняется против версии 1: планировщик обычной цели и приёмка уходят с сильного профиля; у воркера первая
попытка на среднем усилии вместо высокого; появляется четвёртый профиль, выключенный по умолчанию.

## 3. Режим работы над целью

Режим выбирает код по контракту intake и по ходу работы.

| Режим | Когда | Как идёт |
|---|---|---|
| **Соло** | сложность `low` или `medium` (по умолчанию) | один воркер ведёт цель одной сессией по плану-чеклисту с проверками на каждом пункте; затем ревью другим провайдером и приёмка по доказательствам |
| **Команда** | сложность `high`; правило владельца; или соло исчерпало бюджет контекста при незакрытых пунктах | оставшиеся пункты становятся задачами на доске; экземпляры профессий берут их из очереди; параллельно идут только независимые по файлам задачи |

Переход «соло → команда» происходит по факту (исчерпан бюджет контекста сессии, остались пункты), а не по догадке
дешёвой модели о размере. Сделанное в соло остаётся: чеклист и доказательства переносятся в задачи.

В обоих режимах сохраняется то, ради чего Arteliq существует: контракт цели, различающие проверки, независимая
приёмка, журнал. Соло отличается от «просто сессии агента» именно этим контуром.

## 4. Порядок работы

```text
intake (cheap, один вызов)            цель → контракт: критерии, ограничения, сложность
plan   (medium, усилие высокое;       контракт → чеклист (соло) или задачи (команда)
        strong при сложности high)
plan lint (код, без модели)           каждый критерий покрыт проверкой; граф без циклов; программы проверок
                                      существуют; параллельные задачи не пишут в одни файлы
                                      провал → обратно планировщику один раз с перечнем нарушений
work   (medium, усилие среднее)       воркер; свежий контекст на задачу
gates  (код)                          различающие проверки: падают на базе, проходят на результате
review (medium, другой рантайм)       по критериям и чек-листу профиля качества; видит дифф и доказательства
audit  (medium, другой провайдер)     по сводке доказательств постоянного размера, до двух точечных проверок
learn  (cheap)                        навыки и заметки проекта
```

Отдельной «рецензии плана сильной моделью» нет: по измерениям пара «исполнитель + советник» даёт около двух
пунктов качества за двойную цену. Её заменяет проверка плана кодом.

## 5. Лестница эскалации задачи

| Шаг | Условие | Действие | Профиль |
|---|---|---|---|
| 0 | первая попытка | работа по контракту | medium, усилие среднее |
| 1 | проверка или ревью не прошли | повтор с отзывом | medium, усилие высокое |
| 2 | второй провал с той же причиной | «атакуй предпосылку»: диагност проверяет окружение; сбой окружения чинится, попытка не считается | cheap |
| 3 | окружение исправно, третий провал | новая сессия со сводкой попыток | strong, усилие среднее |
| 4 | снова провал | решение менеджера: разделить, переназначить, отменить | strong, по брифу |
| 5 | менеджер исчерпал перепланирования | вопрос владельцу — один, конкретный | — |

Каждый шаг — запись в журнале решений с причиной. Сильный профиль впервые появляется на шаге 3, поэтому в проекте
без застрявших задач сильных вызовов нет вовсе.

## 6. Бюджеты

- **Сильный профиль:** `tiers.expensive_budget_tokens` на проект; на `degrade_at` роли сильного профиля переходят на
  средний, работа не останавливается.
- **Контекст сессии воркера:** потолок оборотов и доля окна; при достижении — сводка и новая сессия (команда) или
  переход в режим команды (соло).
- **Бриф сильной модели:** постоянного размера (≤ 3200 символов), не растёт с проектом.
- **Параллельность:** по спросу в пределах `max_parallel` и лимитов провайдера; рантайм в лимите не получает новых
  экземпляров.

## 7. Как проверяется сама схема

Три варианта на одном сценарии и бюджете, каждый в своей сессии: одна сессия агента без Arteliq; соло; команда.
Сравниваются достижение цели с независимой проверкой, вмешательства владельца, p50 и p95 времени, токены по
профилям. Многомодельная схема остаётся только там, где она лучше каждой одномодельной точки на графике
«результат против затрат». Токены на задачу — не критерий победы команды: по измерениям она дороже одной сессии.
Изменение схемы сначала идёт теневым прогоном рядом с действующей.

## 8. Что работает сегодня и что нет

| Пункт | Сегодня | Этап |
|---|---|---|
| уровни `cheap / medium / expensive` по ролям, бюджет сильной модели, деградация | есть (`artel/routing.py`) | — |
| бриф менеджера и аудитора постоянного размера | есть | — |
| усилие по ролям в конфиге | есть; у воркера высокое с первой попытки | M1 |
| планировщик обычной цели на среднем профиле | только для «простого» запроса | M1 |
| проверка плана кодом | частично: только отсутствующие программы | M1 |
| приёмка другим провайдером | отдельная команда `acceptance verify`, не шаг проекта | M1 |
| режим соло и переход в команду по факту | нет | M1 |
| лестница эскалации: усилие → диагност → сильный профиль | нет: повторы на том же профиле, затем менеджер | M1 |
| три варианта в приёмке | нет | M1 |
| профиль как чистая функция, каталог моделей, `frontier` | нет | M3 |
| экземпляры профессий по спросу | нет | M3 |

Дефекты, найденные при разборе:

1. При работе через API (`provider: anthropic`, свой цикл) таблица моделей по профилям пуста, поэтому каждая роль,
   включая воркеров и библиотекаря, идёт на модели по умолчанию — самой сильной в конфиге. Исправление — в M1.
2. Имя модели по умолчанию записано в коде (`artel/project.py`), а не в каталоге (U8). Исправление — в M3.

## 9. Схемы обмена

**Manager Input** — всё, что видит сильная модель (`Manager.manager_brief`, `Manager.audit_brief`):

```json
{"goal": "≤800 символов", "constraints": ["…"], "success_criteria": ["…"],
 "facts": ["≤7 фактов: вердикты ревью, результаты проверок, счётчики доски"],
 "refs": ["shared/путь", "task:t-…", "run:42"], "open_questions": ["…"],
 "budget": {"expensive_used": 120000, "expensive_limit": 600000}}
```

**Task Contract** — задача на доске (`board.add_task`):

```json
{"id": "t-…", "title": "…", "body": "точный вход", "criteria": ["проверяемые"], "checks": ["команды-гейты"],
 "assignee": "профессия", "depends_on": ["t-…"], "output": "task_submit{summary, evidence}", "max_turns": 40}
```

**Executor Result** — только структура, через терминальный инструмент `task_submit`:

```json
{"summary": "что сделано", "evidence": "команды и их вывод, пути", "files": ["shared/…"]}
```

**Escalation Request** — шаг 4 лестницы: менеджеру уходит бриф, приходит одно решение `replan_decision`:

```json
{"task": "t-…", "reason": "critic_failed | conflict | architecture | risk", "brief": "Manager Input",
 "options": ["retry", "reassign", "split", "cancel", "escalate"],
 "answer": {"action": "split", "rationale": "…", "subtasks": ["Task Contract…"]}}
```

## 10. Конфиг

```yaml
tiers:
  roles: {planner: medium, manager: expensive, auditor: medium, worker: medium, reviewer: medium,
          librarian: cheap, refiner: cheap, doctor: cheap, intake: cheap, concierge: cheap}
  models:
    claude_code: {cheap: haiku, medium: sonnet, expensive: opus}
    native: {cheap: <id модели>, medium: <id модели>, expensive: <id модели>}   # имена провайдера — только здесь
    codex: {}                     # пусто — модель аккаунта Codex
  expensive_budget_tokens: 600000 # на проект
  degrade_at: 0.9
effort: {worker: medium, reviewer: medium, planner: high, manager: medium, auditor: medium}
```

Блок показывает целевые значения. Значения по умолчанию в коде сегодня — версии 1 (планировщик и аудитор на
сильном профиле, воркер на высоком усилии) и меняются в M1 вместе с тестами.
