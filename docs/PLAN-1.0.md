# Arteliq: анализ на 2026-11-10 и план до версии 1.0

Основание: цели и пороги из [SPEC.md](SPEC.md) §1, реестр приёмки
[REGISTRY.md](../bench/acceptance/results/REGISTRY.md), замеры кода на master `48188a0`.
Порядок и статус работ ведёт `roadmap.yaml` ([ROADMAP.md](ROADMAP.md)); этот документ объясняет, почему порядок такой.

## 1. Где проект относительно своих целей

Цель (SPEC §1): идея одной фразой → часы автономной работы на подписке владельца → результат, проверенный
независимо; владелец — заказчик, а не оператор.

| # | Утверждение | Порог | Факт | Статус |
|---|---|---|---|---|
| U1 | проверенный результат | вердикт Critic'а другого провайдера | S-cloud-1: цель достигнута, 6/6 задач; проверка другим провайдером не запускалась (`verdict: null`) | не доказано |
| U2 | долгий горизонт | ≥ 6 ч на L | сценарий L не запускался ни разу | не измерено |
| U3 | экономия дорогой модели | ≤ 5% токенов и вызовов | 27,5% токенов, 17,6% вызовов | провал |
| U4 | токены на задачу | ≤ 0,7 × базовой линии | базовая линия записала 0 токенов; сравнивать не с чем | неизмеримо |
| U5 | автономия | ≥ 95% | 100%, 0 обращений (один прогон) | выполнено на одном прогоне |
| U6 | прозрачность решений | 100% Decision Log | журнала решений нет (`decision_log_coverage: null`) | не начато |
| U7 | независимость от провайдера | S на 3 исполнителях | S пройден только на Claude Code | 1 из 3 |
| U8 | честная архитектура | 0 циклов / 0 глобалов / 0 вендора в логике | 39 рёбер циклов, 19 глобальных объектов, имена вендоров в 15 файлах вне адаптеров; храповик не даёт расти | не выполнено |

Ни одно из восьми утверждений не доказано по правилам SPEC §5: приёмка требует машины владельца, обеих подписок,
трёх прогонов S подряд, контрольной группы и прогона L. Есть один успешный прогон S в облаке без песочницы.

Поставки SPEC §4: сделаны 0 (базовая линия прервана), 1, 2, 3 (этапы A и B), 5 и ворота §11, шаг 1 из 8a.
Не начаты 4, 6, 7, 8, 9, 10 — то есть всё ядро переписывания (каталог моделей, FSM, журнал решений, управление).

## 2. Сильные стороны

1. **Честный контур проверки.** Различающие проверки (падают на базе, проходят на результате), ревьюер, аудитор,
   защищённые файлы проекта, явная модель угроз. Это главное отличие от «агент сказал, что готово».
2. **Автономность на практике.** S-cloud-1: 17 шагов, 0 вопросов владельцу, сбой проверки исправлен командой сама.
3. **Наблюдаемость.** Каждое действие в журнале событий; дашборд, приложение, телефон, Telegram, чат «Спросить»
   читают одну правду.
4. **Инженерная дисциплина.** 1107 тестов, покрытие 80% с храповиком, archcheck, ruff/mypy, CRAP, мутации на
   изменённом коде, CI на трёх ОС, actions по SHA. Дефекты находит собственный прогон (разбор проверок).
5. **Независимость от подписки заложена.** Два CLI-рантайма через один цикл `AgentPort`, отказоустойчивость по
   лимитам, API и локальные модели через openai_compat.
6. **Самоустановка окружения.** Инструменты без sudo, apt через обёртку с белым списком — владелец не ставит руками.
7. **Продуктовая оболочка.** Установка одной командой, окно приложения, уведомления, просмотр файлов, запуск
   результата, оформление, уникальное имя.

## 3. Слабые стороны

Отсортировано по угрозе цели.

1. **Главный тезис не измерен.** Нет контрольной группы: неизвестно, лучше ли команда воркеров одной сессии агента
   с тем же бюджетом. S-cloud-1 стоил $2,31 за утилиту из шести задач; одна сессия могла сделать её дешевле. Пока
   это не измерено, вся конструкция — гипотеза.
2. **Порядок работ не соблюдался.** SPEC §2: всё, что не продвигает приёмку, ждёт. Фактически после заморозки
   сделаны чат, просмотр файлов, приложение, редизайн, переименование, лендинг, пакет. Приоритет № 1 — прогон на
   машине владельца после этапа B — не выполнен ни разу.
3. **Пороги U3 недостижимы арифметически на S.** Проект из 17 шагов: один дорогой вызов — уже 5,9% вызовов. По
   токенам: 5% от 320 тыс. — 16 тыс.; один план занимает 50 тыс. Нужны и изменение конструкции, и уточнение порога.
4. **Переписывание идёт в обратную сторону.** `Manager`, который SPEC §3 заменяет на FSM, вырос с 937 до 1432
   строк; `Evolution` — с 1224 до 1423; `cli.py` 1299, `web/server.py` 994. Новые возможности добавлялись в
   объекты, предназначенные к удалению. `core/` и `shell/` не существуют.
5. **Нет того, что SPEC называет управлением.** Подтверждение Intent, журнал решений, пауза, откат шага, режимы
   автономии, бюджет из панели — ничего из П7.
6. **Долгий горизонт не обеспечен.** Нет сторожа прогресса, возобновление после сна машины или падения процесса
   есть только у эволюции; L на этом не пройдёт.
7. **Известный риск порчи данных в master.** Панель предлагает «Продолжить» проекту, который уже выполняется в
   другом процессе; исправление не закончено.
8. **Два источника плана.** SPEC §4 (поставки) и `roadmap.yaml` (75 пунктов заимствований, 39 в плане) не
   согласованы; публичная дорожная карта не показывала реальный порядок работ.
9. **Публичность без оформления.** Нет лицензии — чужим людям пользоваться кодом нельзя; README и лендинг дают
   `pip install arteliq`, а пакета на PyPI нет (тег `v0.1.0` не отправлен); у репозитория нет описания и тем;
   документация только на русском.
10. **Бюджет разработки не контролируется.** SPEC §4 отводил ≤ 520 тыс. дорогих токенов на всё переписывание и
    «стоп при +20%»; главная сессия исполнителя потратила кратно больше, правило не сработало ни разу.
11. **Два необъяснённых падения CI** (Windows: `test_remote`, WinError 10053; macOS 3.13) закрыты перезапуском —
    это нарушение собственного правила «только причины».
12. **Качество продукта на выходе не задано.** Проверки выдумывает планировщик; профилей качества (П10) нет.

## 5. Определение версии 1.0

1.0 — это не набор функций, а пройденная приёмка SPEC §5 на машине владельца:

- S проходит 3 раза подряд на одной версии, с вердиктом Critic'а другого провайдера и колонкой контрольной группы;
- L работает ≥ 6 ч без остановки по лимиту и проходит U1–U6;
- S проходит на втором провайдере и с локальной моделью в роли исполнителя (U7);
- `archcheck` без базового долга по циклам, глобальному состоянию и вендору (U8);
- посторонний человек ставит Arteliq одной командой на чистой машине и получает первый результат без чтения
  документации; у кода есть лицензия.

## 6. Этапы

Правило: этап закрывается критерием выхода, а не списком сделанного. Следующий этап не начинается, пока не закрыт
текущий. Новые возможности вне этапа не берутся.

| Этап | Суть | Критерий выхода |
|---|---|---|
| **M0. Чистый стол** | слить разбор проверок; закончить блокировку запуска; опубликовать 0.1.0; лицензия, описание и темы репозитория; причины двух падений CI; правила бюджета токенов в CLAUDE.md | в master нет известного дефекта порчи данных; `pip install arteliq` работает; оба падения CI объяснены тестом |
| **M1. Доказательство S** | диета дорогого уровня (план на среднем уровне, дорогая рецензия; аудит по сводке); уточнение порогов U3/U4; предпроверка окружения; раннер контрольной группы; S ×3 у владельца | S проходит 3 раза подряд по согласованным порогам с вердиктом другого провайдера; колонка контрольной группы записана в реестр |
| **M2. Профили качества** (П10) | каталог профилей и генератор проверок; чек-лист ревьюера; дисциплина исправлений; «атакуй предпосылку» у менеджера | эталонные проекты: хороший проходит, испорченный нет; S даёт продукт с чистым линтером, тестами и без находок безопасности |
| **M3. Ядро** (П4, П6) | каталог и профили возможностей; FSM + Orchestrator + расписание команды; сторож и возобновление; `Manager` удалён | все тесты поведения; ни одного класса > 300 строк; базовые файлы archcheck пусты; S не хуже M1 |
| **M4. Управление** (П7) | Intent, журнал решений, пауза/откат/режимы/бюджет, знания по уровням, Attention и outbox, секреты | U6 = 100%; откат возвращает файлы побайтно; сценарный тест на каждую команду |
| **M5. Долгий горизонт** (П8, U2, U7) | приложения над оболочкой; прогон L; S на Codex и на локальной модели | L ≥ 6 ч проходит U1–U6; U7 — 3 из 3 |
| **M6. Выпуск 1.0** (П9) | отчёт приёмки с контрольной группой; английская документация; внешний обзор безопасности; первый запуск для постороннего | критерии раздела 5 |

Правило решения по контрольной группе (фиксируется до прогонов). На S одна сессия может оказаться дешевле — это
ожидаемо для малой задачи и не останавливает работу. Остановка и предложение о переработке — в двух случаях:
Arteliq не проходит независимую проверку там, где её проходит контрольная группа; на L команда не даёт
преимущества ни по достижению цели, ни по вмешательствам владельца.

## 7. Дорожная карта: что изменено

- `roadmap.yaml` остаётся единственным источником порядка и статуса; поставки SPEC внесены в него пунктами этапов
  M0–M6. SPEC хранит контракты поставок, а не их очередь.
- Пункты-заимствования, совпадающие с поставками, привязаны к этапам (конечный автомат задач, аренда файлов,
  сторож, бюджет дерева, рецензия плана, типизированные критерии, вычистка секретов, откат из панели и др.).
- Остальные заимствования перенесены в раздел «После 1.0»: до приёмки они не берутся.
- Удалены два пункта, противоречащие SPEC §2: свой System One и Arteliq как ACP-агент.
- Найденное разбором чужих проектов теперь попадает в «После 1.0», а не перед этапами.

## 8. Решения владельца

| Решение | Рекомендация |
|---|---|
| Лицензия | Apache-2.0: патентная оговорка, совместима с заимствованиями под MIT |
| Пороги U3 | для L оставить ≤ 5%; для S — абсолютный потолок дорогих токенов на проект (предложение: 25 тыс.) и не более двух дорогих вызовов; U4 считать относительно контрольной группы, а не базовой линии с нулевыми счётчиками |
| Заморозка | до выхода из M1 не принимать ни одной новой возможности, включая оформление |
| Публикация 0.1.0 | создать релиз `v0.1.0` на GitHub и pending publisher на PyPI |
| Локальная модель для U7 | любая через Ollama с вызовом инструментов; если её нет — U7 закрывается на двух облачных провайдерах, пункт о локальной модели снимается из критериев 1.0 явно |

## 9. Риски плана

| Риск | Признак | Действие |
|---|---|---|
| Контрольная группа выигрывает и на L | раздел 6, правило решения | остановка, предложение о переработке: Arteliq как контур проверки над одной сессией, а не команда |
| M3 ломает работающее | падение тестов поведения, S хуже M1 | «душитель»: старый модуль удаляется только когда новый прошёл те же тесты; откат ветки |
| Перерасход токенов разработки | главная сессия делает рутину | исполнители на средней модели, главная сессия решает и сливает; ожидание CI одной фоновой командой |
| Подписка меняет условия | лимиты, запрет неинтерактивного режима | вторая подписка и API как равноправные пути (M3, каталог) |
| L не завершается из-за машины | сон, обрыв | сторож и возобновление в M3 до прогона L |
